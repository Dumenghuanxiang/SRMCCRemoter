# SRM 遥控器 1.1 开发复盘

本文记录 SRM 遥控器从原型到当前 1.1 版本的主要技术决策、故障现象、根因和修复方式。重点不是复述界面需求，而是保留以后更换手机、蓝牙模块或单片机时仍然适用的排障经验。

## 1. 最终形态

- Android 横屏遥控器，界面参考 PS5 手柄布局。
- 两颗对称虚拟摇杆、十字键、ABXY 和 6 个开关。
- Material Design 3 与 Material You 动态配色。
- 默认使用 BLE GATT / FFE1，实验性支持 Bluetooth 3.0 SPP。
- 未连接设备时仍可操作，并通过本地回环检查协议帧。
- “SRM校内赛”协议 v3：四轴 `int16`、16 字节 CONTROL 帧、目标频率 1–100 Hz 可调（默认 50 Hz）。
- 可发送 DEBUG 指令，并接收 MCU 的 HELLO、ACK、ERROR 和 LOG。

## 2. 架构概览

```text
触摸事件
  -> GamepadView 更新视觉状态
  -> SrmProtocol 更新最新控制快照
  -> 独立定频调度器按 1–100 Hz 编码 CONTROL（默认周期 20 ms）
  -> GATT / SPP 最新控制帧槽位
  -> 蓝牙模块
  -> MCU UART 环形缓冲区
  -> srm_parser_push()
  -> 原子应用完整控制状态
```

调试消息使用另一条语义不同的路径：

```text
输入 UTF-8 文本
  -> DEBUG 协议帧
  -> 可靠 FIFO
  -> MCU srm_platform_handle_debug()
  -> ACK 或 ERROR
```

CONTROL 是高频、可覆盖的状态快照；DEBUG 是低频、不可覆盖的命令。两者不能共用完全相同的排队策略。

## 3. 主要踩坑与修复

### 3.1 先做控件，再做空间约束，导致互相遮挡

早期把摇杆、开关和调试信息看成彼此独立的组件，结果中间区域向下扩张后覆盖摇杆。横屏高度有限，仅靠固定边距不能保证不同屏幕密度下稳定。

修复方式：

- 先确定顶部操作区、中部开关与日志区、底部摇杆区的纵向预算。
- 摇杆作为最高优先级控件，命中区域和映射半径独立于视觉半径。
- 调试区只显示两行摘要，点击后再进入可选择、可复制的完整窗口。
- 开关阵列和调试面板使用相同宽度基准，避免视觉轴线不一致。

经验：遥控器不是普通信息页。应先锁定操作热区，再安排信息展示区。

### 3.2 Material You 与 Material Design 3 被混为一谈

Material You 主要解决动态取色，Material Design 3 还包括组件形态、层级、状态、间距和交互反馈。只替换颜色并不能让界面符合 MD3。

修复方式：

- 应用继承 `Theme.Material3.DynamicColors.DayNight`，并关闭 ActionBar。
- 使用 `DynamicColors.applyToActivitiesIfAvailable()` 获取系统动态色。
- 显式应用 `ThemeOverlay.Material3.DynamicColors.DayNight`，并移除主题中写死的 `colorPrimary` 和 `colorSecondary`，避免固定色覆盖壁纸色板。
- 监听壁纸变化；未连接时重建当前 Activity 以重新解析动态色资源。控制链路活跃时不为换色强制重建，避免断开遥控连接。
- 设置、扫描、调试等二级操作使用 Material Dialog。
- 状态灯、按钮按压、摇杆偏移和开关变化都提供明确视觉及系统振动反馈。
- 系统支持时使用窗口级模糊，并以动画从浅到深过渡。

经验：动态配色只是主题输入，不能替代组件和交互规范。

### 3.3 把“未连接”错误地等同于“不可操作”

原型曾在没有蓝牙连接时禁用整个控制器。这使 UI 调试、协议验证和演示都依赖真实从机，也让连接故障与控件故障难以区分。

修复方式：

- 主界面不再放置设备选择器，连接管理收进设置页。
- 控件始终可用。
- 未连接时编码相同的协议帧，但写入本地回环日志。
- 状态灯用红、绿、黄区分未连接、已连接和异常。

经验：本地回环不是临时演示功能，而是通信系统的重要诊断边界。

### 3.4 仅凭模块型号或 MAC 地址判断 SPP/BLE

JDY、HC 系列模块存在不同固件和兼容模式。同一商品名称不能证明 Android 侧一定能发现标准 SPP UUID；配对成功也不能证明 RFCOMM 服务可连接。

曾出现以下现象：

- 设备已配对，但未公布 SPP UUID。
- 安全、不安全 RFCOMM 和 channel 1 均在连接后立即关闭。
- 同一 MAC 能发现 FFE1 GATT 服务，因此设备最初看起来“被识别成 BLE”。
- `1234` 是经典蓝牙配对码，只影响配对，不会修复不存在或不可用的 RFCOMM 服务。

修复方式：

- 默认按实际可发现的 FFE1 GATT 服务连接。
- SPP 保留为设置中的实验模式，并明确警告恢复步骤。
- 扫描结果展示名称、地址、RSSI、配对状态和传输类型，避免仅显示设备名。
- 连接失败详情进入可复制调试窗口，Toast 只显示短摘要。

经验：传输能力必须通过 Android 实际发现的服务和特征验证，不能根据标签推断。

### 3.5 GATT 特征能找到，不代表写法正确

找到 FFE1 后曾发生 `FFE1 write rejected`。GATT 特征可能支持 `WRITE`、`WRITE_NO_RESPONSE`，或同时支持两者；不同写法的完成语义和吞吐完全不同。

修复方式：

- 连接后检查特征 properties。
- CONTROL 在支持时使用 `Write Without Response`。
- HELLO 和 DEBUG 优先使用需要确认的可靠写入。
- ATT Payload 按 20 字节分片；MCU 端将收到的数据视为连续字节流，不假设一次回调等于一帧。
- GATT 内部写入计时放到专用线程，不借用 UI 主线程。

经验：UUID 只说明“找到了谁”，properties 和写入回调才说明“应该怎么写”。

### 3.6 FIFO 对调试命令正确，对遥控状态错误

初版 GATT 和 SPP 都会把 CONTROL 逐帧放入 FIFO。当实际链路短暂低于 50 Hz 时，旧摇杆状态持续积压。从机虽然仍在收包，但收到的是几百毫秒前的数据，表现为明显延迟。

修复方式：

- CONTROL 使用单个“最新帧槽位”。新状态覆盖尚未发出的旧状态。
- HELLO、DEBUG 等事务消息继续使用可靠 FIFO。
- 恢复吞吐后发送最新状态，不补发已经过期的运动轨迹。

经验：实时控制系统优先保证信息新鲜度，而不是保证每个历史采样都到达。

### 3.7 50 Hz 心跳放在 UI Handler，周期发生漂移

使用 `postDelayed(20 ms)` 时，下一次延时从本次任务执行结束后开始计算；界面重绘、日志刷新或弹窗动画都会拉长实际周期。

修复方式：

- 使用独立 `ScheduledExecutorService.scheduleAtFixedRate()`。
- `SrmProtocol` 对共享状态和序号进行同步或原子访问。
- 断开连接时立即取消任务，Activity 销毁时关闭调度器。

经验：UI Handler 适合界面工作，不适合承担硬实时含义的周期发送。

### 3.8 9600 bps 的 50 Hz 预算非常紧

UART 采用 9600 8N1，每字节实际占 10 bit：

```text
可用吞吐 = 9600 / 10 = 960 bytes/s
CONTROL   = 16 bytes
50 Hz     = 800 bytes/s
占用率    = 83.3%
理论上限  = 60 frames/s
```

这意味着下行只剩约 160 bytes/s。最大 DEBUG 帧、额外 ACK 或自定义文本都可能造成短时控制间隔变大。

修复方式：

- CONTROL 不返回 ACK。
- DEBUG 必须低频，并接受其发送期间控制更新短暂变慢。
- MCU 日志限速，运动期间避免连续输出大段文本。
- MCU 使用环形缓冲区逐字节解析，不能在中断中执行复杂命令。

经验：理论可达不等于工程上有充足余量。50 Hz 是当前 16 字节协议在 9600 bps 下的高占用工作点。

### 3.9 从 int8 升级 int16 后，旧节流阈值失效

摇杆从 `int8` 改为 `int16` 后，输出范围扩大约 256 倍，但变化阈值仍是 2。一次像素移动通常已变化约百个数值，导致几乎每个 MotionEvent 都触发后续处理。

修复方式：

- 保留线上的完整 `int16`。
- 将事件变化阈值调整到 32；它仍小于当前物理像素对应的量化变化。
- 真正的发送频率由设置中的 1–100 Hz 定频采样决定，而不是由 MotionEvent 数量决定。

经验：扩大数据精度时，要同步检查死区、阈值、滤波和日志频率，不能只修改字段类型。

### 3.10 17 字节协议在 9600 bps 下余量过小

四个 `int16` 加上按键、开关、十字键和通用帧头后，早期 CONTROL 达到 17 字节。50 Hz 需要 850 bytes/s，占 UART 有效带宽约 88.5%。

修复方式：

- ABXY、S1-S6 和 D-pad 共 13 bit，压入一个小端 `uint16`。
- CONTROL Payload 压缩到 10 字节，完整帧 16 字节。
- 保留双同步字节、版本/类型、序号、长度和 CRC8。

经验：协议压缩应优先利用字段真实取值范围，不应先牺牲同步和校验能力。

### 3.11 调试日志反过来阻塞遥控输入

本地回环最初在每次摇杆移动时执行：编码、转十六进制、追加日志、重建最多 500 条历史、刷新多个 TextView。按钮和十字键也经过同一路径，因此所有控件都出现卡顿。

修复方式：

- 控制状态立即更新，主界面命令文本限频刷新。
- 连续本地回环历史限制到 10 Hz，按下和松开等离散事件仍即时记录。
- 删除每次追加都重建完整日志字符串的无效工作。
- 完整日志只在展开窗口中显示，主界面只保留摘要。

经验：日志属于观测路径，绝不能改变被观测的实时行为。

### 3.12 自定义 View 强制软件渲染并在 onDraw 中分配对象

手柄为了阴影效果曾调用 `LAYER_TYPE_SOFTWARE`，同时每帧创建多个 Gradient 和 Path。高分辨率横屏下，拖动摇杆会反复重绘整张手柄。

修复方式：

- 恢复硬件加速。
- 静态预渲染手柄外壳、按键底座和摇杆底座。
- 缓存 L/R 普通与按下状态的摇杆帽纹理。
- 使用 `postInvalidateOnAnimation()` 合并同一显示帧内的刷新。
- 只标记当前控件的脏区域，并只复制静态位图的对应区域。

经验：`onDraw()` 应避免对象分配；复杂而不变的装饰层应缓存，动态层应尽量小。

### 3.13 把两种“自动重连”混成一个设置

“启动时连接上次设备”和“运行中意外断联后持续重试”具有不同风险。前者只发生一次，后者可能长期耗电、反复报错；早期设置只有前者的开关，但用户容易理解成两种行为都受控。

修复方式：

- “启动时自动重连”仅在 Activity 首次创建时尝试保存的设备。
- “意外断联后自动重连”仅在本次会话曾成功连接后，响应非用户触发的链路错误；首次连接失败不会进入无限重试。
- 断联重连使用 1、2、4、8、15 秒退避，之后保持 15 秒上限。
- 用户主动断开、切换 GATT/SPP、重新选择设备时立即取消待执行重试。
- 连接成功后清零重试次数。

经验：自动化功能必须区分用户意图和故障恢复，不能只看当前是否处于断开状态。

### 3.14 App 把输入方向擅自解释成车辆动作

十字键上、下、左、右曾显示为“前进、后退、左转、右转”，松开显示“停止”。这把某一种从机映射写进了通用遥控器，后续把按键用于云台、机械臂或菜单时会产生错误语义。

修复方式：

- App 只显示“十字键 上/下/左/右/中立”。
- 摇杆只显示左右摇杆及轴值。
- ABXY 只描述按下或松开，开关只描述自身状态。
- 运动学含义、通道混控和执行机构映射全部由 MCU 工程定义。

经验：上位机协议层应描述输入事实，不应推断下位机业务含义。

### 3.15 用限频掩盖 100 Hz 断联，违背设置语义

JDY-31 / BLE FFE1 的实测吞吐低于 70 Hz，但用户把目标设为 100 Hz 时，App 仍必须按
100 Hz 调度。把内部上限偷偷改成 60 Hz 只能暂时减少错误，既欺骗设置界面，也没有解决
异常断联后的恢复问题。

真正的问题是旧 GATT 回调、延迟写入任务、新连接和 Activity 销毁可能交错：一次异常
断联后开始重连，旧会话仍可能改变新会话状态；销毁后的晚到回调还可能向已关闭的控制
调度器提交任务。

修复方式：

- 每次 GATT 连接分配递增 generation，所有回调和延迟写入都验证 GATT 实例与 generation。
- 关闭连接时统一清空写队列、最新 CONTROL、写入状态和延迟任务，并容忍厂商蓝牙栈在 `close()` 时抛出的运行时异常。
- 控制调度任务内部捕获运行时异常；Activity 销毁后拒绝重新启动已关闭的调度器。
- 手动扫描期间抑制断联自动重连，避免用户新连接与后台旧连接竞争。
- 保留 100 Hz 真实调度语义；链路忙时只覆盖未发送的旧 CONTROL，不形成延迟队列。

经验：设备链路达不到目标频率时，应暴露真实测量值并保证恢复能力，不能通过未声明的
限频把生命周期缺陷藏起来。

### 3.16 扫描结果合并刷新导致快速点击闪退

为了减少扫描期间 UI 刷新，设备名称、RSSI、排序和列表通知最初全部延迟 200 ms 合并。
但是新设备已经先加入 `ArrayList`；若用户此时触摸 `ListView`，Adapter 报告的旧数量与
实际列表数量不一致，小米 Android 16 会抛出
`The content of the adapter has changed but ListView did not receive a notification`。

修复方式：

- 新设备改变列表数量时立即调用 `notifyDataSetChanged()`。
- RSSI、名称变化和排序仍按 200 ms 合并，保留扫描性能优化。
- 点击时从 Adapter 的 `getItemAtPosition()` 取得当时显示的项，不直接按位置读取可变列表。
- 扫描停止后忽略晚到 BLE 回调；停止扫描捕获厂商栈可能抛出的 `RuntimeException` 并写入调试日志。

经验：列表内容数量变化和 Adapter 通知必须同步；可延迟的是非结构字段，不是可见项的增删。

### 3.17 嵌套设置页只刷新文字，没有刷新操作

设置页打开时曾只在当时已经连接的情况下创建“断开当前设备”按钮。从设置进入扫描页并
连接成功后，底层设置 Dialog 没有重建，连接回调只能更新状态文字，所以必须退出并重新
进入设置才能看到断开按钮。

修复方式：设置页始终创建断开按钮，断开状态时隐藏并禁用；连接状态刷新入口同时更新
状态文字、按钮可见性和可用性。Dialog 关闭时按实例清理引用，防止晚到蓝牙回调更新旧窗口。

经验：长期存在的二级界面必须渲染完整状态，而不能把条件式 View 创建当作状态管理。

### 3.18 模糊动画必须覆盖返回手势的完整生命周期

只实现弹窗进入时从浅到深的模糊，会让淡出显得突兀；固定时长的退出动画又会拖慢频繁
操作。全面屏预测性返回还允许手势开始后取消，简单监听最终 Back 事件无法正确恢复界面。

修复方式：

- 进入时在零模糊首帧之后渐变到系统支持的窗口模糊半径。
- 普通退出使用较短的 140 ms 模糊、遮罩和内容透明度动画。
- 预测性返回进度实时反向驱动模糊和遮罩；手势取消后用 180 ms 恢复当前 Dialog。
- 系统不支持跨窗口模糊时只保留遮罩动画，不生成假的静态模糊图。

经验：返回手势不是只有“退出”一个结果，动画状态必须支持开始、推进、取消和完成。

## 4. 当前协议边界

- App 版本：1.1。
- 协议版本：SRM校内赛 v3。应用版本和协议版本不是同一个概念。
- CONTROL：16 字节，默认 50 Hz，四轴 `int16` 小端。
- App 的 CONTROL 目标频率可在 1–100 Hz 间以 1 Hz 步进调整；实际吞吐受链路限制，9600 bps 建议不超过 50 Hz。
- BLE 与 SPP 都对尚未发送的 CONTROL 使用“最新状态覆盖”，高于链路能力的设置不会形成历史状态队列。
- 设置中的“向已连接从机下发控制帧”默认开启；关闭后仍可操作控件和发送 DEBUG，但 MCU 会在 600 ms 后进入安全状态。
- JDY-31 / BLE FFE1 在串口提高至 115200 bps 后，实测控制帧频率仍低于 70 Hz，说明此时瓶颈已从 UART 转移到 BLE GATT、系统调度或模块转发链路；实际使用建议设为 50–60 Hz。
- DEBUG：UTF-8 Payload，最多 64 字节，不包含隐式 `\0`；默认追加 LF，可在设置中关闭。下位机命令例程兼容无换行、LF 和 CRLF。
- CRC：CRC-8/ATM，多项式 `0x07`。
- CONTROL 超时：MCU 600 ms 未收到合法帧后进入安全状态。
- v2 与 v3 不兼容，MCU 和 App 必须同时升级。

完整线协议见 [SRM_CAMPUS_COMPETITION_PROTOCOL.md](SRM_CAMPUS_COMPETITION_PROTOCOL.md)。

## 5. 下位机实现注意事项

1. 蓝牙模块 UART 设置为 9600 8N1。
2. UART ISR 只收字节并写入环形缓冲区。
3. 主循环逐字节调用 `srm_mcu_rx_byte()`。
4. 只有完整帧通过 CRC 和字段校验后，才一次性替换控制状态。
5. `srm_platform_handle_debug()` 必须使用显式长度，不能假设 Payload 以 `\0` 结束。
6. CONTROL 不回复 ACK；DEBUG 成功回复 ACK，失败回复 ERROR。
7. 记录 CRC 错误、序号跳变、实际频率和最长控制间隔，比只打印“收到数据”更有诊断价值。

## 6. 发布前验证清单

- Android 单元测试通过。
- `lintRelease` 无错误。
- R8 release 构建通过。
- 在真机验证动态浅色和深色主题。
- 在目标 JDY 设备验证 FFE1 properties 包含预期写入能力。
- 静止和双摇杆运动时分别统计至少 60 秒 CONTROL 频率。
- 测量从触摸变化到 MCU 应用状态的延迟，不只统计包数。
- 发送最大长度 DEBUG，确认控制只短暂降速且不产生持续积压。
- 主动断开、模块掉电、手机关闭蓝牙后均能进入安全状态并恢复重连。
- 扫描结果刚出现时立即连续点击设备，确认列表不会崩溃且只启动一次有效连接。
- 从设置页进入扫描并连接，返回同一个设置页后状态和“断开当前设备”按钮必须立即更新。
- 在支持预测性返回的设备上分别验证完成和取消手势，确认模糊与遮罩都能恢复。
- 使用正式 keystore 签名，并离线备份 keystore、alias 和密码。

## 7. 可复用结论

- 先验证实际服务和特征，再决定设备属于 SPP 还是 GATT。
- 高频状态与低频命令必须采用不同可靠性和排队策略。
- 9600 bps 下协议长度、日志量和 ACK 策略都是实时控制的一部分。
- 本地回环、可复制日志和连接状态灯应在早期加入，而不是发布前补做。
- 性能问题要同时观察 UI 主线程、RenderThread、蓝牙写队列和 MCU UART，单看某一层容易误判。
- 对遥控器而言，最新状态和确定的失联保护比“每一帧都送达”更重要。
